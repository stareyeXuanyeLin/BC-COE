# 2026-07-30 会话记录：RVP/1 协议硬切重构

## 会话目标

本次要求为：

- 不保留 RVS/4 兼容层；
- 不继续围绕旧分片队列修补参数；
- 直接硬切主版本；
- 完成协议相关代码重构；
- 运行测试、构建和语法检查；
- 将结果提交到 Git `dev` 分支。

## 重构前的问题

旧协议的流程是：

```text
STATE → REQUEST → 为每个接收者单独发送完整 CHUNK 序列
```

同一份快照被每个接收者分别复制传输。设房间中有 `P` 个 COE 节点，每份快照需要 `C` 个分片，初始同步消息量近似为：

```text
M旧 = P + P(P-1)(C+2)
```

其中包括广播 STATE、STATE 回应、REQUEST 和逐接收者 CHUNK。

以 6 个 COE 节点、每份快照 8 个分片为例，理论上可达到约 306 条协议消息；单个客户端的理论出站量约 51 条。BC R130 的原生发送队列共享 14 条 / 1200ms，人数增加后，快照消息会和其他游戏及 Mod 消息共同进入 FIFO 队列。

旧版的 8 片 burst、250ms 分批、12 条 / 1200ms COE 窗口和按请求重试，只能控制重复流量，无法消除“同一快照按接收者复制”的乘法项。

## 新协议

新协议名称：

```text
COE_RVP/1
Remote Visual Publication Protocol
```

旧协议已硬切移除：

```text
COE_RVS/4 不再注册、不再解析、不再发送、不再回退
```

新消息类型：

```text
D  DISCOVER
A  ADVERTISE
W  WANT
X  DATA
N  NACK
R  REVOKE
```

### 新流程

小快照：

```text
ADVERTISE（内联 gzip 数据）
→ 解压、校验、缓存、激活
```

大快照：

```text
ADVERTISE
→ 第一个接收者广播 WANT
→ 发布者广播一套 DATA
→ 所有接收者共同组装和验收
```

同一 ObjectId 在一个同步波次中只发布一套完整 DATA，不再为每个接收者分别发送。

### 内容寻址

快照对象身份为：

```text
ObjectId = SHA-256(canonical 未压缩快照 UTF-8)
```

远端状态拆分为：

```text
Discovery       节点能力与接收意愿
Publication     发送者当前 session/revision/ObjectId
Assembly        Sender/ObjectId 的临时分片组装
ObjectCache     已验证不可变对象
ActiveBinding   MemberNumber 当前激活对象
```

同一 hash 的已验证对象可以在本地缓存中复用，但缓存节点不能替原始发布者发送 DATA。

## 代码变更

### `src/11-remote-protocol.js`

- 协议 namespace 改为 `COE_RVP/1`；
- 删除 STATE、REQUEST、CHUNK、CLEAR envelope；
- 增加 D/A/W/X/N/R envelope；
- 增加 gzip Compression Streams 编解码；
- 增加压缩输入、解压输出、inline、分片和 chunk 数预算；
- 保留并复用原有严格 snapshot schema、canonical、SHA-256、Property 和原型污染防护；
- gzip 只改变传输编码，不改变快照 hash 身份。

### `src/12-remote-store.js`

- 删除 pending request 与逐请求 assembly 模型；
- 改为 Publication、Discovery、ObjectCache、ActiveBinding、ObjectId assembly；
- 支持同 hash 缓存命中；
- 支持 revision/hash/metadata 冲突拒绝；
- 支持同片幂等、冲突片隔离、对象级 DATA 预算；
- room generation 会清理远端发布、组装、激活和 WANT/NACK 状态。

### `src/13-remote-transport.js`

- 删除 COE 自有快照队列、burst、250ms timer 和独立 12/1200ms 窗口；
- DATA 批次直接提交给 BC `ServerSend` 原生队列；
- 增加共享 DATA 发送；
- 增加匹配 Advertisement 的对象级数据接收预算；
- 保留 Hidden handler、Sender 校验、错误隔离和 late handler retry。

### `src/14-remote-controller.js`

- 重写为 DISCOVER、ADVERTISE、WANT、DATA、NACK、REVOKE 状态机；
- 小对象支持 ADVERTISE 内联；
- 第一个 WANT 触发共享 DATA 发布；
- 2 秒 cohort 窗口内合并重复 WANT；
- 缺片最多一轮 NACK 修复；
- WANT 无 DATA 时最多一次延迟重试；
- dirty 快照在 DISCOVER 响应前共用 in-flight build；
- 初始房间同步只发送一次 DISCOVER 和一次当前 ADVERTISE；
- 新成员加入本身不再自动逐成员发送协议消息；
- 远端快照激活仍通过 `CharacterRefresh(character, false, false)`，不写正式 Appearance。

### `src/15-bootstrap.js`

- 更新测试 API 导出；
- 暴露新 Publication/ObjectCache/Assembly 操作；
- 更新本地远端状态测试结构，增加 compressed bytes。

## 测试变更

重写了协议、Store 和 Transport 测试，并更新远端渲染相关测试的激活方式。

新增覆盖：

- RVP/1 namespace；
- gzip 编解码与预算；
- Publication revision/hash/metadata 冲突；
- DATA 乱序重组；
- 重复片与冲突片；
- 无 Advertisement 的 DATA 拒绝；
- ObjectCache 跨发布复用；
- 内联 Advertisement 直接激活；
- 多个 WANT 只产生一套共享 DATA；
- DISCOVER 不形成 ping-pong；
- NACK 精确缺片修复；
- DATA 对象级发送预算；
- 普通成员加入不产生额外协议流量；
- dirty 快照在 DISCOVER 响应前立即重建；
- 初始房间同步只产生 DISCOVER 与当前 Advertisement。

## 后续实机验证重点

代码重构完成后，仍需在真实 BC 环境测试：

1. 双账号小快照内联路径；
2. 双账号大快照分片路径；
3. 六人房间，1 发布者 + 1 接收者 + 4 普通账号；
4. 六人房间，多个 COE 发布者与接收者同时同步；
5. 发布端或接收端处于后台标签页；
6. 晚加入者 DISCOVER 与定向 Advertisement；
7. 连续编辑产生 revision 更新；
8. 快速换房、离房、断线和重连；
9. 与 BCX、LSCG、WCE、Echo 等 Mod 同时运行；
10. 记录 COE `ServerSend` 调用、Hidden 到达、DATA 数量、ObjectId 验收和纹理加载时间。

重点验收指标：

```text
同一发布者、同一 ObjectId、同一同步波次：完整 DATA 广播次数 <= 1
多个接收者不应导致完整 DATA 按接收者复制
加入普通账号不应显著增加 COE DATA 数量
后台标签页不应出现 COE timer 每片额外等待
旧 generation 不得重新激活远端对象
```
