# COE 远端自定义服装交互协议重设计研究

> 日期：2026-07-30  
> 性质：纯研究与协议设计，不包含任何代码修改  
> 研究对象：BC-COE-dev 当前 `COE_RVS/4` 远端视觉快照协议  
> 目标：在 3 人以上房间中消除随接收者数量急剧放大的快照传输成本

---

## 1. 结论先行

当前性能问题来自协议拓扑，而非某个定时器参数或队列实现细节。

`COE_RVS/4` 把一份本质上相同、不可变的快照，分别放进每个“发送者 → 接收者”点对点会话中传输。房间人数增加后，同一份快照被重复编码为多组定向 CHUNK；同时，每一对节点还要交换 STATE、STATE 回应和 REQUEST。消息量由服装大小和接收者数量相乘，初始多人同步甚至呈二次增长。

推荐放弃 RVS/4 的“逐接收者快照会话”框架，建立新的 **房间级内容寻址发布协议**，暂称：

```text
COE_RVP/1
Remote Visual Publication Protocol
```

核心语义：

1. 一份快照是由 SHA-256 标识的不可变内容对象；
2. 发布者公布对象清单，房间中的接收者共同消费同一次数据发布；
3. 同一发布版本在一个房间同步波次中只广播一次，不为每个接收者复制完整 CHUNK；
4. 小快照直接内联在公告中，一条消息完成加载；
5. 大快照经过 gzip 后广播分片；
6. 缺失数据使用 WANT/NACK 请求，接收者之间可观察并抑制重复请求；
7. 修复数据仍由原始发布者发送，缓存节点不得替他人重新发布，保持 BC Sender 身份边界；
8. 快速路径不依赖 `setTimeout`、`setInterval` 或 `requestAnimationFrame`；
9. BC 自带 `ServerSend` 队列负责最终 14 条/1200ms 的发送约束，COE 不再建立一套基于后台计时器的精细分片节拍器；
10. 房间切换、重连和发布者离开仍通过 room generation 彻底失效。

在所有 COE 节点都分享一份快照的理想同步波次中，数据消息复杂度由：

```text
RVS/4：O(P² × C)
```

降为：

```text
RVP/1：O(P × K)
```

其中：

- `P` 是协议参与节点数量；
- `C` 是当前未压缩快照分片数；
- `K` 是新协议 gzip 后分片数，通常小于 `C`；
- 复杂度改善首先来自“一份数据只发布一次”，压缩负责继续缩小常数。

## 2. 现有协议的真实结构

### 2.1 当前消息

RVS/4 使用：

```text
STATE
REQUEST
CHUNK
CLEAR
```

典型流程：

```text
A 广播 STATE
B 收到 A 的 STATE
B 定向回复自己的 STATE
B 定向 REQUEST A 的 hash/revision
A 为 B 单独排入一整套 CHUNK
B 重组、校验、激活快照
```

如果 C、D、E 也需要 A 的同一份快照，则 A 会再为每个人分别排入一整套相同 CHUNK。每套 CHUNK 只有 `requestId` 和目标不同，内容本身完全相同。

### 2.2 当前硬限制

源码中的关键限制为：

```text
Content 协议预算：1800 字符
快照 canonical 上限：32768 UTF-8 bytes
每片 data：1200 base64url 字符
最多：32 片
BC 客户端共享发送窗口：14 条 / 1200ms
COE 当前自限：12 条 / 1200ms
公开服务端默认连接上限：20 条 / 秒，超限可能断线
```

当前发送器虽然做了控制队列与快照队列分离、8 片 burst、轮转公平和按进度重试，但这些机制只是在管理重复流量，无法消除重复流量。

### 2.3 RVS/4 的二次消息增长

假设：

- 房间中有 `P` 个同时参与分享与接收的 COE 节点；
- 每份快照平均需要 `C` 个 CHUNK；
- 每对节点都需要对方的当前快照。

初始同步近似消息量：

```text
初始广播 STATE：P
每对节点的 STATE 回应：P(P-1)
每对节点的 REQUEST：P(P-1)
每对节点的快照 CHUNK：P(P-1)C
```

合计：

```text
M旧 = P + P(P-1)(C+2)
```

单个客户端同时作为发布者和接收者时，理论出站量近似：

```text
M旧_单端 = 1 + (P-1)(C+2)
```

示例：

| COE 节点 P | 平均分片 C | 房间协议消息 M旧 | 单端理论出站 |
|---:|---:|---:|---:|
| 2 | 2 | 10 | 5 |
| 4 | 8 | 124 | 31 |
| 6 | 8 | 306 | 51 |
| 6 | 20 | 666 | 111 |
| 10 | 8 | 910 | 91 |

这解释了“三人附近开始恶化”的现象。人数跨过某个点后，单端消息量超过 BC 的共享窗口，后续消息进入原生 FIFO 队列；后台标签页又会让 COE 自己的延时批次按约 1 秒粒度执行，加载时间开始阶梯式增长。

### 2.4 当前方案无法通过调参根治

修改以下参数只能移动临界点：

```text
8 片 burst 改成 12 片
250ms 改成 100ms
12 条/1200ms 改成 14 条/1200ms
12 秒重试改成 20 秒
```

只要协议仍然为每个接收者复制一遍完整快照，发送成本仍含有 `(P-1) × C`。复杂服装、更多接收者或第三方 Mod 流量最终会再次突破队列窗口。

## 3. 已确认的外部约束

### 3.1 BC 客户端发送队列

R130 本地源码显示：

```js
var ServerSendRateLimit = 14;
var ServerSendRateLimitInterval = 1200;
```

`ServerSend()` 会先压入全局 `ServerSendRateLimitQueue`，随后立即调用 `ServerSendQueueProcess()`。队列允许时，同一执行回合可以连续发送多条；超出窗口的消息留在 FIFO 中。

BC 还通过 Game Worker 驱动后台 `GameRunBackground()`，其中继续调用 `ServerSendQueueProcess()`。因此 BC 自身已经为后台标签页提供低频队列泵。COE 再建立依赖页面主线程计时器的精细节拍器，会形成两层调度并增加不确定性。

### 3.2 浏览器后台计时器

Chrome 官方说明：隐藏页面中的 JavaScript timer 会被批量检查；普通节流状态通常按 1 秒检查，隐藏超过 5 分钟并满足条件时，链式 timer 可能按 1 分钟检查。

因此新协议的快速成功路径不得依赖：

```text
每 100～400ms 发送下一批
等待精确 debounce 后才开始数据传输
依靠 requestAnimationFrame 推进网络状态机
短周期轮询查看队列是否清空
```

Timer 只适合作为超时清理和失败修复兜底，不能承担正常传输进度。

### 3.3 BC 服务端

公开服务端源码当前显示：

```text
ChatRoomChat Content 最大 2000 字符
连接默认所有消息合计 20 条/秒
Target 为空时向当前房间广播
Target 为 MemberNumber 时只路由到房内目标
Sender 由服务端账号连接生成
```

广播路径已经提供“发送一次、房间多人接收”的网络原语。RVS/4 使用广播只发送小 STATE，却把真正昂贵的数据限定为定向传输，没有利用最有价值的底层能力。

### 3.4 压缩能力

MDN 记录 Compression Streams API 自 2023 年 5 月起达到跨浏览器广泛可用，可在主线程或 Web Worker 中使用 gzip/deflate。

本研究使用合成的 COE 结构数据进行了本地 gzip 估算。结果只代表结构可压缩性，不代表真实衣柜统计：

| 合成结构 | canonical JSON | 当前 base64 分片 | gzip 后 base64 分片 |
|---|---:|---:|---:|
| 4 materials / 16 layers | 2361 B | 3 | 1 |
| 8 materials / 32 layers | 4731 B | 6 | 1 |
| 16 materials / 64 layers | 9493 B | 11 | 2 |
| 30 materials / 120 layers | 17832 B | 20 | 2 |

高随机字符串的压力样本中，gzip 后仍可能需要 5～17 片。因此压缩不能取代正确的拓扑设计，但很适合把真实、重复字段较多的 COE JSON 压到 1～4 条消息。

## 4. 候选架构比较

### 4.1 方案 A：保留点对点 Pull，只增加 gzip

流程：

```text
STATE → REQUEST → 定向 gzip CHUNK
```

优点：

- 与 RVS/4 最接近；
- 改造范围较小；
- 大多数服装的 C 会显著下降。

缺点：

- 同一压缩对象仍按接收者重复发送；
- 复杂度仍为 `O(P² × K)`；
- 只减少常数，未消除多人放大；
- 用户要求放弃旧框架，此方案不符合目标。

结论：不采用。

### 4.2 方案 B：每次变化都主动广播完整压缩快照

流程：

```text
本地变化 → gzip → 广播完整对象
```

优点：

- 最简单；
- 一次发布供全房间接收；
- 无 REQUEST 往返；
- 数据复杂度为 `O(P × K)`。

缺点：

- 房间中没有接收插件时仍发送大数据；
- 新加入或晚启用接收的客户端需要触发重播；
- 大快照的广播与修复语义不完整；
- 频繁编辑时需防止连续发布旧 revision。

结论：拓扑正确，但需要按需发现、缓存和修复机制，单独使用过于粗糙。

### 4.3 方案 C：内容寻址公告 + 房间级发布 + NACK 修复

流程概念：

```text
发布者公告 hash/revision/encoding/size
小对象直接内联
大对象由第一个 WANT 触发一次房间广播
其他接收者观察 WANT 并抑制重复请求
所有接收者共同组装同一 hash
缺片者发送 NACK；发布者广播缺片修复
```

优点：

- 数据发布由点对点复制变成房间级共享；
- 内容 hash 天然支持去重和缓存；
- 小对象一条消息完成；
- 没有逐片 ACK；
- 快速路径事件驱动，不需要 timer 推进；
- 新加入、晚启用、缓存命中和缺片修复都有明确语义；
- 可保持 Sender 必须等于原始发布者的安全边界。

缺点：

- 协议状态机与 RVS/4 不兼容；
- 需要定义同一 hash 的发布波次和重复 WANT 抑制；
- 广播 CHUNK 会被未启用接收的房间成员收到，但 Hidden 消息不会显示，未安装插件客户端只会由 BC 内建路径吞掉；
- 大量 COE 发布者同时更新时仍需全局拥塞策略。

结论：推荐。

### 4.4 方案 D：WebRTC、外部 CDN 或专用中继

优点：

- 可绕开 BC ChatRoomChat 的 2000 字符与队列限制；
- 理论吞吐更高。

缺点：

- 增加信令、NAT、隐私、基础设施与可用性问题；
- WebRTC 会形成新的连接生命周期和攻击面；
- 外部中继需要维护服务器并持久接触用户生成数据；
- 与当前“轻量、房间瞬时、无额外服务”的边界不符。

结论：不采用。

### 4.5 方案 E：使用大型 Dictionary 或 Appearance 承载

Dictionary 可绕过 Content 的窄限制，但只受更大的 socket.io 总包限制；Appearance 则会重新污染正式角色状态。

结论：两者都不采用。协议仍使用有明确长度预算的 Hidden Content。

## 5. 推荐协议：COE_RVP/1

### 5.1 基本对象模型

协议不再把 `(sender, receiver, requestId)` 当作快照传输主键，而使用：

```text
ObjectId = SHA-256(canonical uncompressed snapshot)
Publication = sender session + revision + ObjectId
```

同一 `ObjectId` 表示完全相同的不可变快照内容。revision 只表示发布者当前状态的先后，不参与内容身份。

接收端状态分离为：

```text
PeerPublication：某发送者当前指向哪个 ObjectId
ObjectCache：某 ObjectId 的已验证不可变内容
Assembly：某 ObjectId 的临时分片组装状态
ActiveBinding：某角色当前激活哪个 ObjectId
```

一个对象可被多个公告或缓存条目引用；对象校验一次后无需为每个请求重复 JSON parse、schema normalize 与 hash。

### 5.2 建议消息类型

名称仅为研究草案，可在实施评审时进一步压缩字段。

#### DISCOVER

```js
{
  t: "D",
  s: peerSession,
  rx: true,
  caps: ["gz"]
}
```

用途：

- 客户端入房完成后广播一次；
- 接收功能从关闭变为开启时广播一次；
- 表明自己能够接收 RVP/1 与支持的编码；
- 不做对称回复，不形成 HELLO ping-pong。

#### ADVERTISE

```js
{
  t: "A",
  s: publisherSession,
  r: revision,
  h: objectHash,
  u: uncompressedBytes,
  e: "gz",
  b: encodedBytes,
  n: chunkCount,
  d: optionalInlineData
}
```

用途：

- 发布者状态变化时广播；
- 收到新成员 DISCOVER 时可定向补发当前公告；
- `d` 存在时，公告本身就是完整对象；
- 同 `(sender, session, revision, hash)` 公告幂等。

#### WANT

```js
{
  t: "W",
  o: ownerMemberNumber,
  s: publisherSession,
  r: revision,
  h: objectHash
}
```

用途：

- 只针对未内联且本地无缓存的对象；
- 建议广播，而非定向；
- 其他接收者看到相同 WANT 后，取消自己的重复 WANT；
- 原始发布者看到第一个有效 WANT 后发布数据；
- 发布者对同一 ObjectId 的并发 WANT 合并为一个 publication flight。

WANT 中的 `o` 只用于路由意图。真正可以响应并产生有效 DATA 的身份仍必须是 BC 服务端提供的 Sender 等于 `o` 的原始发布者。

#### DATA

```js
{
  t: "X",
  s: publisherSession,
  r: revision,
  h: objectHash,
  i: chunkIndex,
  n: chunkCount,
  d: chunkData
}
```

用途：

- 原始发布者广播 gzip+base64url 分片；
- DATA 不再绑定某个 receiver 的 requestId；
- 房间内所有等待同一 ObjectId 的接收者共同消费；
- 同 index 同内容幂等；冲突片使该 Sender/ObjectId assembly 失败。

#### NACK

```js
{
  t: "N",
  o: ownerMemberNumber,
  s: publisherSession,
  r: revision,
  h: objectHash,
  miss: [[start, end]]
}
```

用途：

- 只在完整对象迟迟无法完成时请求缺片；
- 使用区间或 bitset 表示缺片，不逐片发送 ACK；
- 建议广播，其他缺失相同范围的接收者可抑制自己的 NACK；
- 发布者合并一小段时间内收到的缺片集合，广播修复片；
- 若 timer 被后台节流，只会推迟异常修复，不影响正常完整广播路径。

#### REVOKE

```js
{
  t: "R",
  s: publisherSession,
  r: revision
}
```

用途：

- 关闭分享、当前无可见自定义服装或明确撤销发布；
- 只解除该发送者的 ActiveBinding；
- 不必立即删除 ObjectCache，缓存按 LRU/TTL 回收。

### 5.3 小对象内联

如果压缩后的 base64url 数据与 ADVERTISE envelope 合计不超过 Content 安全预算，则：

```text
ADVERTISE + inline data
```

一条广播即可让所有接收者完成：

```text
解析 envelope
→ base64url 解码
→ gzip 解压
→ canonical/schema/hash 校验
→ 激活
```

无需 WANT、DATA、重试或 timer。

合成结构测试显示，真实 COE JSON 中大量重复键、组名和图层字段适合 gzip；常见服装很可能落入 1 条内联或 1～2 个 DATA 分片。该判断仍需用去标识化真实样本验证，不能把合成结果当作正式容量承诺。

### 5.4 大对象发布

大对象流程：

```text
A 广播 ADVERTISE(hash, sizes, chunkCount)
B/C/D 发现本地无 hash
最先发出的接收者广播 WANT(A, hash)
其他接收者看到 WANT 后抑制自己的相同请求
A 将该 hash 标记为 in-flight
A 在当前执行回合把所有 DATA 交给 ServerSend
BC 原生队列按自身窗口发送
B/C/D 同时组装并校验
```

COE 不再用 250ms timer 手工推进每一批。原因：

1. BC 已有共享发送队列；
2. BC 会立即发送窗口内消息；
3. 超出窗口的数据自动排队；
4. BC Game Worker 会在后台继续泵队列；
5. gzip 后的正常对象应尽量落在一个 BC 窗口内；
6. 再套一层 timer 只会增加延迟和状态竞态。

需要保留 COE 自身的“单次发布最大消息数”和“每个房间 generation 最大在途字节数”，但不需要精确模拟 BC 的发送时钟。

### 5.5 发布更新

本地编辑产生新 revision 时：

```text
500ms 用户编辑防抖可以保留
→ 构建最新 canonical
→ gzip
→ hash
→ 广播内联 ADVERTISE，或 ADVERTISE 后按需发布 DATA
```

编辑防抖允许 timer，因为它只合并用户操作；即使后台延迟，也不会把一个已经开始的数据传输拆成多个 1 秒间隔。入房、新 DISCOVER 或明确同步请求发现 dirty 状态时，应立即共用一个 in-flight build，而不是等待防抖 timer。

旧 revision 尚未开始发送时直接丢弃；已经进入 BC 原生队列的旧消息无法撤回，接收端依靠 revision/hash 拒绝旧对象激活。ObjectCache 可以保留旧 hash，但 ActiveBinding 只能指向最新有效 revision。

### 5.6 新加入与晚启用

新客户端：

```text
ChatRoomSync 完成
→ 安装 handler 并建立 room generation
→ 广播 DISCOVER
→ 现有发布者定向发送当前 ADVERTISE
→ 小对象直接内联完成
→ 大对象由 WANT 触发一次定向补发或房间广播
```

建议规则：

- 房间中已有一批接收者同时需要该对象时，使用广播 DATA；
- 只有一个晚加入者缺失、其他人已有缓存时，可以定向 DATA；
- 选择广播或定向只是传输优化，DATA 校验和 ObjectId 语义保持相同；
- 发布者可依据该 ObjectId 在本 room generation 是否刚刚广播过来选择模式，不需要接收者逐个 ACK。

### 5.7 修复而非重传整个对象

底层 WebSocket/socket.io 在正常连接上可靠有序，缺片更可能来自：

```text
接收 handler 安装太晚
Sender 尚未进入本地 ChatRoomCharacter
room generation 切换
本地预算拒绝
协议消息损坏或冲突
```

因此无需把协议设计成不可靠 UDP 的完整重传系统。NACK 只作为应用层状态缺失修复：

- 首次正常 DATA 不逐片 ACK；
- assembly 知道 `n` 后可计算缺片；
- NACK 合并多个缺片范围；
- 相同 ObjectId 的广播 NACK 可被其他接收者观察并抑制；
- 发布者只修复当前 session/revision/hash；
- 修复一轮后仍失败，可请求整对象一次；
- 最多一轮缺片修复和一轮完整重发，之后本地放弃并诊断；
- 任何修复都不能无限循环。

这借鉴了可靠组播中的 NACK suppression 思想，但不实现 NORM、FEC 或拥塞控制全套协议。BC 房间最多几十人、底层又是可靠 socket，FEC 的实现成本高于收益。

---

## 6. 新旧复杂度比较

理想同步波次中，假设每位发布者：

- 发送 1 条 ADVERTISE；
- 房间只产生 1 条有效 WANT；
- gzip 后为 `K` 条 DATA。

则：

```text
M新 ≈ P(K+2)
```

若对象可以内联：

```text
M新_inline ≈ P
```

示例比较：

| P | RVS/4 C | RVS/4 消息 | RVP/1 K | RVP/1 消息 | 下降 |
|---:|---:|---:|---:|---:|---:|
| 4 | 8 | 124 | 2 | 16 | 87.1% |
| 6 | 8 | 306 | 2 | 24 | 92.2% |
| 10 | 8 | 910 | 2 | 40 | 95.6% |
| 6 | 20 | 666 | 5 | 42 | 93.7% |

这是理想上界模型，真实运行还会有：

```text
DISCOVER
定向补发公告
重复但被合并的 WANT
NACK 修复
成员快速进出
不同客户端缓存命中差异
```

即使控制消息不能完全线性化，只要完整 DATA 不再按每个接收者复制，最昂贵的乘法项就已经消失。

### 6.1 单发布者、多接收者场景

当前 RVS/4 中，一个发布者面对 `R` 个接收者时，数据出站为：

```text
R × C
```

RVP/1 同步波次中为：

```text
K
```

例如 5 个接收者、当前 8 片、gzip 后 2 片：

```text
当前：40 条 DATA
新协议：2 条 DATA
```

这正是多人房间性能问题最直接的改善。

## 7. 流控设计

### 7.1 不再复制 BC 的时钟

新协议不应保留：

```text
每 250ms 下一 burst
固定 12/1200ms 的独立滑动窗口
依靠 timer 的 round-robin batch
```

建议保留的是面向对象和波次的离散预算：

```text
单对象最大 canonical 大小
单对象最大 compressed 大小
单对象最大 chunk 数
单 sender 同时最多一个 publication flight
单 room generation 同时最多若干 assembly
每次本地 revision 只允许一个待发布对象
旧 revision 排队前可取消
WANT/NACK 每 sender/hash 冷却
房间总缓存与在途字节预算
```

这些预算限制“能做多少工作”，BC 队列负责“具体何时发出”。

### 7.2 控制消息优先级

如果仍建立一个极薄的 COE 出站层，优先级应是：

```text
REVOKE / 最新 ADVERTISE
DISCOVER / WANT
NACK repair
DATA
```

但该层只做：

```text
旧 revision 去重
同 hash WANT 合并
同 hash NACK 合并
generation 失效
```

不负责用 timer 模拟发送速率。

### 7.3 大对象保护

即使 canonical 允许 32 KiB，也应单独设置 compressed 上限与 chunk 上限。例如研究阶段可测试：

```text
inline：总 Content <= 1800
常规 publication：gzip base64url <= 6～8 片
扩展 publication：最多 16～20 片
```

最终数值必须由真实数据分布和压力测试决定。不能仅凭合成 gzip 比例直接冻结。

若对象超过远端预算：

- 本地服装功能继续正常；
- 远端分享暂停该版本；
- 明确告诉用户“远端快照压缩后仍超过上限”；
- 不截断、不静默发送不完整服装、不把超限数据转移到 Dictionary。

## 8. 安全与一致性不变量

新协议改变拓扑，不应放松现有安全边界。

### 8.1 Sender 所有权

有效 ADVERTISE、DATA、REVOKE 必须满足：

```text
BC data.Sender == 当前房间成员 MemberNumber
```

对象缓存可以跨发送者按 hash 复用解码结果，但远端角色绑定仍由真实 Sender 的 Publication 决定。

缓存节点不得替原发布者发送 DATA。否则接收端无法区分“某人发布了这件服装”和“第三方声称替她发布”。

### 8.2 完整性

hash 始终针对：

```text
严格规范化后的未压缩 canonical JSON UTF-8
```

接收顺序：

```text
原始 Content 预算
→ envelope schema
→ base64url 预算
→ gzip 解压输出预算
→ UTF-8 fatal decode
→ JSON parse
→ snapshot schema
→ canonical 再序列化相等
→ SHA-256 相等
→ ObjectCache
→ ActiveBinding
```

gzip 不能引入解压炸弹风险，必须在流式读取或 Response 输出后检查严格的解压字节上限；仅检查压缩输入大小不够。

### 8.3 生命周期

所有状态绑定：

```text
roomGeneration
sender MemberNumber
publisherSession
revision
ObjectId
```

换房、离房、断线：

- 立即解除 ActiveBinding；
- 清除 publication flight、WANT、NACK 和 assembly；
- 旧异步 gzip/hash/parse 完成后不得重新激活；
- ObjectCache 可作为纯内容缓存保留，但不能跨房自动绑定角色。

### 8.4 资源预算

建议继续保留或重新定义：

```text
materials/layers 上限
单 material 引用预算
canonical 总字节
compressed 总字节
解压输出字节
每 sender assembly
房间 assembly 数
ObjectCache LRU/TTL
房间 ActiveBinding 总字节
诊断条数
```

广播 DATA 不再有 pending requestId 作为接收授权，因此接收端必须要求：

```text
已见到该 Sender 的匹配 ADVERTISE
或本地存在针对该 Sender/ObjectId 的有效 WANT/NACK
```

对完全无公告、无需求的 unsolicited DATA，可以只做轻量识别后丢弃，防止广播洪泛强迫所有客户端分配 assembly。

## 9. 迁移策略

RVP/1 与 RVS/4 的核心语义不同，不建议在同一个状态机中兼容两者。

### 9.1 推荐：传输双栈、状态机隔离

过渡版本可同时注册两个 namespace：

```text
COE_RVS/4|
COE_RVP/1|
```

但必须是两个隔离 controller：

- RVP/1 客户端之间只使用新协议；
- 对明确只支持 RVS/4 的旧客户端，才启用旧点对点流程；
- 同一远端角色优先 RVP/1，收到新协议有效发布后停止该角色的 RVS/4 请求与渲染绑定；
- 两套协议不得共享 request、assembly 或 revision 状态；
- 旧协议兼容应有删除期限。

问题：旧客户端无法主动声明“不支持 RVP/1”。过渡版本需要短暂发送一个小型 RVS/4 STATE 或能力标记来发现旧节点，这会保留少量旧控制流量；但新客户端之间的数据必须立即走 RVP/1，不能为兼容而同时发送两份完整快照。

### 9.2 激进方案：主版本硬切

直接停止 RVS/4，只支持 RVP/1。

优点：

- 实现最干净；
- 不会因旧协议兼容继续制造多人拥堵；
- 更容易验证安全状态机。

代价：

- 新旧版本之间暂时互不可见；
- 用户需要统一更新。

如果 COE 的加载器能可靠自动更新，而且当前 Remote 仍处于快速开发阶段，硬切比长期双栈更合理。

### 9.3 不推荐：RVS/4 envelope 内塞新消息

不要把广播对象、压缩、NACK 和内容缓存逐步塞进 `COE_RVS/4`。这会让同一个主版本拥有两种互斥语义，接收端难以判断 DATA 是点对点请求响应还是房间级发布，也会使安全预算和回归测试成倍复杂。

## 10. 实施前验证计划

本研究不修改代码。进入实现前，应先用探针验证下列假设。

### 10.1 数据集统计

从测试者主动导出的去标识化快照样本统计：

```text
canonical bytes 分布：P50/P90/P99/max
gzip bytes 分布：P50/P90/P99/max
base64url 后分片数分布
materials/layers 分布
压缩与解压耗时
hash/schema 校验耗时
```

禁止直接扫描或上传用户本地衣柜。样本应由测试者明确导出，并只保留协议 canonical 数据。

### 10.2 Hidden 广播压力探针

只发送固定重复文本，不发送真实服装，测试：

```text
1、2、4、8、14 条同步 ServerSend
前台与后台标签页
2、4、6、10 人房间
接收端到达顺序与间隔
BC 原生队列是否阻塞普通聊天/角色更新
是否出现 ForceDisconnect / ErrorRateLimited
```

重点确认：同步交给 BC 队列是否比 COE timer 分批更稳定。

### 10.3 协议模拟器

实现代码前先写独立纯状态机模拟：

场景至少包括：

```text
6 个节点同时 DISCOVER
同一 ADVERTISE 触发多个并发 WANT
WANT 在 DATA 前后乱序到达
重复 DATA
缺 1 片、缺多片
NACK 重复与合并
发布过程中出现新 revision
发布者离房
接收者晚启用
快速换房后旧 gzip/hash promise 完成
一个恶意 sender 广播无公告 DATA
```

验收指标：

```text
同 hash 同一波次只产生一次完整广播
没有逐接收者完整 DATA 复制
无逐片 ACK
无无限重试
旧 generation 永不激活
任何单 sender 错误不影响其他 sender
```

### 10.4 实机阶段

建议顺序：

1. 双账号、1 个小对象；
2. 双账号、最大对象；
3. 六人房，1 发布者 + 1 接收者 + 4 普通账号；
4. 六人房，3 发布者 + 3 接收者；
5. 六人房，所有 COE 节点同时分享；
6. 后台标签页；
7. 与 BCX、LSCG、WCE、Echo 等共同运行；
8. 连续编辑产生 revision 风暴；
9. 快速进出房间与重连。

每轮同时记录发布端和接收端：

```text
COE 调用 ServerSend 时间
BC 原生队列长度与窗口时间（若只读探针可安全获取）
接收 Message Handler 时间
ObjectId assembly 完成时间
解压、校验、CharacterRefresh 时间
总消息数、DATA 数、重复 WANT/NACK 数
```

## 11. 成功标准

新协议进入实现阶段后，必须以数量级指标验收，不能只看“双人房感觉变快”。

### 11.1 消息规模

同一发布者、同一 ObjectId、同一同步波次：

```text
完整 DATA 广播次数 <= 1
```

允许：

```text
一次缺片修复
一次晚加入者定向补发
```

不允许：

```text
每个接收者各一套完整 DATA
```

### 11.2 延迟

对 gzip 后不超过一个 BC 窗口的对象：

```text
正常路径不应等待 COE timer 才发送下一片
```

后台标签页中的主要延迟应只剩：

```text
BC 原生队列窗口
网络与服务器转发
接收端解压/校验
纹理加载
```

### 11.3 房间人数敏感度

在只有一名发布者和一名接收者时，加入 4 个普通账号不应显著增加 COE 协议 DATA 数量。

在多个 COE 接收者同时需要同一发布者对象时，发布者 DATA 出站量应与接收者数量基本无关。

### 11.4 正确性

- 新旧 revision 不倒退；
- sharing 关闭及时撤销；
- 缓存命中不绕过 Sender publication；
- 缺 Asset 仍按现有规则局部跳过并报告；
- 不写 Character Appearance；
- 未安装插件用户不看到 Hidden 正文；
- 不因异常远端数据中断 BC ChatRoomMessage 主循环。

---

## 12. 明确不做的事情

本次重设计应明确排除：

1. 继续微调 RVS/4 的 burst/window/retry 参数；
2. 为每片 DATA 增加 ACK；
3. 使用 `requestAnimationFrame` 推进传输；
4. 使用静音音频或 WebRTC 规避后台节流；
5. 直接调用 `ServerSocket.emit` 绕过 BC 队列；
6. 把完整快照放进大型 Dictionary；
7. 通过 Appearance Bundle 传播协议数据；
8. 允许缓存节点冒充原始发布者转发对象；
9. 为小房间设计一套、多人房间再设计另一套互不兼容协议；
10. 在没有真实 gzip 分布与六人实测前冻结最终字节、分片和超时数值。

---

## 13. 最终建议

建议把下一阶段定义为一次主版本级重构，而非 RVS/5 小修：

```text
旧：Peer Session Transfer
STATE → REQUEST → per-target CHUNK

新：Room Content Publication
DISCOVER → ADVERTISE/INLINE → shared DATA → NACK repair
```

设计中心从“我该如何更快地把 32 片分别发给五个人”变成：

```text
这五个人需要的是同一件不可变内容，为什么要发送五遍？
```

BC 已经提供房间广播，COE 应把服务器当作房间级扇出器；hash 让对象可去重，gzip 降低分片常数，WANT/NACK suppression 控制反馈，room generation 和 Sender 校验维持安全边界。

这条路线真正移除了多人性能问题中的乘法项。后续即使仍需调整 inline 阈值、最大压缩字节或 NACK 超时，那些也只是在一个线性框架中校准参数，不会再次回到人数一多就按二次项恶化的旧结构。
