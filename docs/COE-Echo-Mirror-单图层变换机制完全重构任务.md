# COE-Echo-Mirror 单图层旋转与缩放机制完全重构任务

> 目标项目：`BC-Plugin/COE-Echo-Mirror`
>
> 执行窗口：新窗口
>
> 本文用途：交给新的分析窗口，重新设计并实现单图层旋转、缩放与变换中心机制。
>
> 重要要求：本任务不应继续沿用当前窗口已经尝试过的修补方案。需要从 BC 的实际绘制链路、坐标空间和矩阵语义重新建立设计。

---

## 一、当前结论

此前针对“变换中心”的修复方案已经实际尝试，但问题没有得到解决，现有实现不能继续作为可靠基础。

当前仍存在以下问题：

1. 单个图层的旋转和缩放输入框输入数值后，数值无法正确保存，或者保存后不生效。
2. 通过“✚ 中心”十字光标设置出的中心点，并不是真正参与旋转和缩放的中心点。
3. 设置中心点后进行旋转，图层会发生平移。
4. 图层旋转、缩放、中心点之间的关系不符合用户直觉，也不符合“围绕同一中心旋转和缩放”的要求。
5. 之前增加的几何采集、canvas 坐标映射、GLDrawImage 包装和逆矩阵推导没有证明与 BC 实际渲染矩阵一致。

因此，本次任务目标不是继续修复某一个加法、除数或坐标转换，而是完全重构单图层变换机制。

---

## 二、必须保留的核心语义

### 2.1 单一 pivot

每个单图层只允许有一个变换中心：

```text
同一个 pivot 同时作为旋转中心和缩放中心。
```

不能分别设置 rotation pivot 与 scale pivot，也不能让旋转和缩放各自走不同坐标系。

### 2.2 手动中心必须真实生效

用户在输入框或十字光标中设置中心后：

- 旋转必须围绕该中心进行。
- 缩放必须围绕该中心进行。
- 中心位置不能因为旋转自动漂移。
- 中心位置不能因为缩放自动漂移。
- 改变旋转角度时，图层的中心锚点在画布中应保持不变。

### 2.3 输入框和实际渲染必须是同一份状态

输入框写入的值必须：

1. 进入当前编辑中的 layer 数据。
2. 立即影响预览渲染。
3. 在 UI 重绘后仍然存在。
4. 保存到 composition 后仍然存在。
5. 重新打开方案后仍然存在。
6. 通过远程快照发送后仍然能够在接收端还原。

任何只修改 DOM 输入框、只修改临时对象、或只修改渲染 options 而没有写回正式 layer 数据的方案都不可接受。

## 三、必须先废弃或重新验证的旧假设

新窗口不得直接假设下面这些做法是正确的：

### 3.1 不能假设 `DrawingLeft/Top + offset` 就是真实绘制位置

BC 的最终绘制位置可能经过：

- `DrawPose`
- `PropertyLayerOrigin.resolveLayer`
- `CanvasUpperOverflow`
- `PoseRecord[*].MovePosition`
- `FixedPosition`
- 角色高度比例
- `BodyStyle.DrawOffset`
- 属性覆盖
- Mirror / Invert
- CommonDraw 内部的其他位置修正

必须确认最终送入 BC 图像绘制函数的坐标含义。

### 3.2 不能假设 callback 的 `X/Y` 可以直接作为 GL 图像左上角

需要验证：

- CommonDraw 的 `drawImage` 回调参数是否就是最终画布坐标。
- 回调坐标和 `GLDrawImage` 的 `dstX/dstY` 是否完全相同。
- `offsetX` 参数属于 BC 的画布偏移，还是另一个局部坐标。
- Mirror / Invert 是在进入 GLDrawImage 前发生，还是在矩阵中发生。
- callback 的 options 是否包含完整的 BC 原生变换状态。

### 3.3 不能继续以“自定义 GLDrawImage 包装”作为默认正确路径

之前的方案通过包装 `GLDrawImage` 并自行构造矩阵，但当前表现证明这条路径至少存在严重语义错误。

新设计必须先回答：

1. BC 原生图像绘制是否已经有旋转、缩放或中心参数。
2. 是否可以通过 BC 原生 options 实现变换，而不重复构造一套 GL 矩阵。
3. 如果必须使用自定义矩阵，顶点坐标、纹理坐标、矩阵乘法顺序、坐标原点、Y 轴方向是否已经通过源码和实验确认。
4. 是否因为原始 BC 绘制已经执行过一次，再叠加自定义矩阵导致双重变换。
5. 是否因为 GL uniform 或 program 状态被其他绘制步骤覆盖，造成输入参数和视觉结果不一致。

### 3.4 不能继续用经验除数修正拖拽

禁止继续使用类似：

```js
clientDelta / 100
clientDelta / 150
clientDelta / DrawingWidth
clientDelta / DrawingHeight
```

除非明确说明两个坐标空间、比例来源和矩阵逆变换关系，并有独立测试证明。

## 四、需要重新建立的底层模型

新窗口首先要建立一套清晰的变换模型，至少区分以下坐标空间。

### 4.1 纹理本地坐标

以纹理左上角为原点：

```text
localTexture = (u, v)
```

需要明确：

- `u/v` 是像素还是归一化坐标。
- Mirror / Invert 是否改变该坐标的方向。
- pivot 是位于完整纹理范围，还是位于可见内容范围。
- 纹理实际宽高来自哪里。

### 4.2 BC 绘制前坐标

图层经过 BC 的姿势、属性和位置解析后，得到一个未经自定义旋转缩放的绘制矩形：

```text
baseRect = { x, y, width, height }
```

必须确认这个矩形的来源和每个字段的坐标空间。

### 4.3 变换中心坐标

建议明确记录两种值：

```text
pivotLocal     // 纹理本地坐标，或纹理归一化坐标
pivotCanvas    // 变换前/变换后画布坐标中的中心
```

最终只能选一种作为持久化主语义，另一种必须由当前几何重新计算。

不能让持久化数据同时保存两个可能互相矛盾的中心。

### 4.4 画布坐标

需要区分：

- canvas 内部像素坐标。
- CSS 显示坐标。
- client 坐标。
- BC 逻辑绘制坐标。
- GL viewport 坐标。

必须明确每一次转换的方向，不允许依赖“看起来差不多”。

## 五、建议优先研究的实现路线

新窗口应至少比较以下路线，再选择最终方案。

### 路线 A：完全使用 BC 原生绘制 options

研究 BC 是否已有：

- Rotation
- Scale
- Origin
- Pivot
- Offset
- Mirror
- Invert

如果 BC 原生能力足够，应优先注入 BC 原生参数，避免重复实现 GL 矩阵。

需要确认：

- 原生参数的单位。
- 原生 pivot 的原点。
- 原生 rotation 的方向。
- 原生 scale 是否围绕固定中心。
- 是否支持单个合成图层而不影响其他图层。

### 路线 B：在 BC 图像绘制入口前统一替换一次矩阵

如果 BC 原生能力不足，必须保证：

1. 原始图像只绘制一次。
2. 自定义矩阵只作用于当前 COE 合成图层。
3. 不重复调用原始绘制造成颜色或纹理副作用。
4. 自定义矩阵的输入与原始绘制矩形来自同一次调用。
5. 所有变换都由一个统一矩阵完成。

建议使用明确的矩阵语义：

```text
finalPoint = overallMatrix * localMatrix * basePoint
```

其中单图层场景可以先只实现：

```text
finalPoint = T(pivot) * R(rotation) * S(scale) * T(-pivot) * basePoint
```

并通过数值测试验证：

- pivot 点变换前后完全不动。
- rotation = 0、scale = 1 时图层完全不变。
- rotation = 90° 时方向符合 BC 坐标系。
- scale = 2 时 pivot 到任意点的距离变为 2 倍。

### 路线 C：先在离屏 canvas 合成，再交给 BC 绘制

只有在 BC GL 路径难以安全接入时才考虑。

需要评估：

- 性能。
- 着色和透明度。
- Mirror / Invert。
- 远程角色绘制。
- 姿势变化。
- 纹理加载和缓存。

本路线不能因为实现简单就直接采用，必须确认不会破坏 BC 原有颜色和绘制语义。

## 六、输入框失效问题的专项排查

新窗口必须单独追踪从输入框到最终渲染的完整数据链：

```text
input event
  ↓
当前编辑 layer
  ↓
editing composition
  ↓
normalizeComposition
  ↓
activeComposition
  ↓
buildLocalSyntheticItems
  ↓
source layer / visual proxy
  ↓
CommonDraw callback
  ↓
GLDrawImage 或 BC 原生绘制
```

逐层确认：

1. 输入事件的 field 名称是否与数据字段一致。
2. `pivotX/pivotY` 是否在 normalize 时被删除。
3. `rotation/scale` 是否因为“接近默认值”逻辑被删除。
4. `refreshPreviewLoop()` 是否重新创建了旧 layer，覆盖了输入值。
5. `editing`、`activeComposition`、渲染时 normalize 后的对象是否为不同副本。
6. 保存时是否调用了错误的 composition 对象。
7. `compactCompositionForStorage()` 是否保留输入值。
8. renderer 是否从另一个旧对象读取变换。
9. GL options 是否被 BC 后续逻辑覆盖。
10. 视觉没有变化时，究竟是数据没写入，还是矩阵没有生效。

必须为每一个阶段增加可测试的纯函数或最小化日志，不允许只靠肉眼判断。

---

## 七、十字光标问题的专项排查

十字光标目前只是一个 fixed DOM 元素，必须确认它到底代表什么：

1. 鼠标当前位置。
2. 当前输入的 pivot 在画布中的位置。
3. 图层局部 pivot 映射到画布后的实际位置。
4. 变换后 pivot 的最终位置。

这四者不能混为一谈。

新的交互设计必须明确：

- 按下十字按钮时，初始十字位置从哪里读取。
- 拖动过程中，十字位置是否是 canvas 坐标映射后的结果。
- 释放鼠标后，十字位置是否由实际保存的 pivot 重新计算。
- 旋转后，十字位置是否仍然落在图层真实旋转中心。
- 缩放后，十字位置是否仍然落在图层真实缩放中心。
- 当前没有有效渲染几何时，是否禁止写入，而不是使用猜测坐标。

禁止出现“十字光标显示在 A 点，但实际矩阵围绕 B 点运行”的状态。

## 八、建议的数据模型

在没有完成底层验证前，不要急于改协议。建议先在内部建立清晰的运行时模型：

```js
{
  targetKind: "layer",
  layerIndex: 0,
  layerKey: "...",
  baseRect: {
    x: 0,
    y: 0,
    width: 100,
    height: 100
  },
  pivot: {
    // 只选一种作为持久化主语义，另一种仅作为运行时派生值
    localX: 0.5,
    localY: 0.5
  },
  rotation: 0,
  scale: 1,
  mirror: false,
  invert: false,
  matrix: null
}
```

推荐持久化仍兼容现有字段：

```text
layer.rotation
layer.scale
layer.pivotX
layer.pivotY
```

但必须先定义这些字段的唯一单位和语义，并在文档中固定下来。

不得为了临时修复再添加第二套含义不明的 `screenPivot`、`rotationPivot`、`scalePivot` 字段。

## 九、必须具备的纯函数测试

### 9.1 变换矩阵

至少覆盖：

1. identity 变换保持所有点不变。
2. pivot 点经过任意旋转仍保持原位。
3. pivot 点经过任意缩放仍保持原位。
4. 旋转与缩放组合时 pivot 仍保持原位。
5. 90°、180°、270° 的方向正确。
6. 正负角度方向符合 BC 实际坐标系。
7. scale 0.25、1、2、3 正常。
8. Mirror / Invert 与旋转组合正确。
9. 无效宽高不会产生 NaN 或 Infinity。
10. 矩阵正向变换和逆变换可以互相还原。

### 9.2 输入到数据

覆盖：

1. 输入 rotation 后 layer.rotation 立即更新。
2. 输入 scale 后 layer.scale 立即更新。
3. 输入 pivot 后 layer.pivotX/pivotY 立即更新。
4. UI 重绘不丢值。
5. normalize 不丢值。
6. compact storage 不丢值。
7. 重新加载后值保持。

### 9.3 拖拽到 pivot

覆盖：

1. CSS canvas 缩放时位置仍准确。
2. 画布左上、中心、右下位置准确。
3. Mirror 后 X 方向正确。
4. Invert 后 Y 方向正确。
5. 已有 rotation 时拖动仍能得到正确局部 pivot。
6. 已有 scale 时拖动仍能得到正确局部 pivot。
7. rotation 与 scale 同时存在时拖动仍能得到正确局部 pivot。
8. 没有渲染几何时不会写入错误值。

## 十、BC 手工验收标准

完成实现后，必须在 BC 中实际执行以下流程：

### 10.1 基础旋转

1. 添加一个宽度明显大于高度的图层。
2. 设置中心为纹理左上角。
3. 旋转 90°。
4. 确认左上角保持在原中心位置，图层围绕该点旋转。
5. 设置中心为纹理右下角，重复测试。

### 10.2 基础缩放

1. 设置中心为纹理外部一点。
2. 缩放到 0.5。
3. 缩放到 2.0。
4. 确认图层始终围绕同一中心缩放。
5. 确认中心点自身不发生漂移。

### 10.3 输入框

1. 直接输入 rotation。
2. 直接输入 scale。
3. 直接输入 pivotX/pivotY。
4. 观察预览是否立即变化。
5. 离开输入框并触发 UI 重绘。
6. 保存方案。
7. 关闭并重新打开方案。
8. 确认所有数值和视觉结果保持。

### 10.4 十字光标

1. 进入单图层变换中心编辑。
2. 将中心拖到图层左上角。
3. 旋转 90°。
4. 将中心拖到图层右下角。
5. 缩放到 2.0。
6. 确认十字光标表示的位置就是实际旋转和缩放中心。

### 10.5 姿势与显示比例

1. 切换多个姿势。
2. 改变浏览器窗口尺寸。
3. 改变 UI 显示比例或 canvas CSS 尺寸。
4. 重复中心、旋转和缩放测试。
5. 确认同一个持久化 pivot 在新的姿势下仍遵循定义好的语义。

### 10.6 远程兼容

1. 保存含有自定义 pivot、rotation、scale 的方案。
2. 发送到远端角色。
3. 接收端验证图层中心和变换结果。
4. 验证旧快照没有新增字段时仍可显示。

## 十一、完成标准

新重构只有在以下条件全部满足后才算完成：

- 输入框数值能够写入正式 layer 数据。
- 输入框数值能够影响实际预览。
- UI 重绘不会覆盖输入值。
- 保存、重新打开后数值不丢失。
- 十字光标对应真实变换中心。
- 旋转不会因为自定义中心产生额外平移。
- 缩放不会因为自定义中心产生额外平移。
- 旋转和缩放严格共享同一个 pivot。
- 变换矩阵经过纯函数测试和 BC 手工测试。
- 不再依赖经验除数。
- 不再依赖未经验证的 `DrawingLeft/Top` 猜测作为最终几何。
- 不会对同一图层重复应用 BC 原生变换和 COE 自定义变换。
- 旧存储数据和旧远程快照仍能读取。
- 新协议字段只有在确认确实需要时才增加。
- 不实现素材服装组级变换，不借用整体字段伪装单图层组变换。

## 十二、新窗口建议执行顺序

```text
1. 阅读本任务文档及现有变换相关源码
2. 检查当前工作区差异，区分已有改动与本次重构改动
3. 追踪 BC 原生 CommonDraw / GLDrawImage / PropertyLayerOrigin 的真实调用链
4. 通过最小实验确认 X/Y、纹理尺寸、Mirror、Invert 和旋转方向
5. 暂停 UI 修改，先定义唯一的坐标空间和 pivot 语义
6. 编写纯函数矩阵与逆矩阵测试
7. 编写输入框数据流测试
8. 选择并实现单一变换路线
9. 先只支持单图层 rotation / scale / pivot
10. 完成单图层 BC 手工验收
11. 再恢复远程同步兼容
12. 最后评估是否保留整体变换相关代码
```

本任务的核心原则：先证明坐标和矩阵语义，再写代码；先让单个图层的中心、旋转、缩放完全正确，再考虑整体变换、远程同步和更多交互。
