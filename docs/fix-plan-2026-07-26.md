## P0 渲染正确性

### 1. 整体变换中心与 BC 实际绘制坐标不一致

**文件** `src/02-data.js:193-217` `computeDefaultOverallCenter()`

**问题** 当前代码只读取了 `DrawingLeft` / `DrawingTop` 的姿势解析值，没有复现 BC 完整坐标管线中额外叠加的：

- 当前姿势的 `PoseDef.MovePosition`
- `FixedPosition` 造成的 `fixedYOffset`
- `CanvasUpperOverflow`
- BodyStyle 的 `DrawOffset`
- 角色高度比例相关偏移

**实测** 设置 `CanvasUpperOverflow=300` 后，插件返回 `centerY=60`，而实际绘制中心至少在 `360`。

**影响** 整体旋转/缩放会围绕错误中心作用，不同姿势漂移，远程两端中心都不一致。

**修复方向**

- 方案 A：在真实 CommonDraw 回调中记录解析完成的 X/Y，以实际绘制几何计算中心
- 方案 B：复用 BC 当前 `CommonDrawComputeDrawingCoordinates` 坐标逻辑，包含姿势位移、身体偏移和高度修正
- 把 `CanvasUpperOverflow` 等因素作为已知常数纳入 fallback

### 2. WebGL 镜像图层的 blink 绘制坐标错误

**文件** `src/07-renderer.js:306-314`

**问题** Mirror + blink 同时生效时偏移值计算顺序不同。

当前 COE 顺序：

```js
drawX = dstX + off          // 先加 blink offset
if (mirror) drawX = 500 - drawX  // 再镜像
```

BC 原生 `GLDrawImage` 顺序：

```js
if (Mirror) dstX = 500 - dstX
matrix = m4.translate(matrix, dstX + offsetX, dstY, 0)  // 镜像后再加 offset
```

**结果** Mirror=true, offsetX=500, dstX=100 时：BC 原生得到 `900`，当前插件得到 `-100`。

**影响** 镜像服装的 blink 图层被送到画布以外，表现为镜像消失、闪烁残影或错位。

**修复方向** 改为与 BC 原生一致的顺序：

```js
var drawX = mirror ? 500 - dstX : dstX;
drawX += off;
```

## P1 远程同步状态机

### 3. 新 REVISION 到达时旧 CHUNK 分片导致首片丢失

**文件** `src/12-remote-store.js:84-118`

**问题链**

1. 正在组装旧请求 `req_A`（`addRemoteChunk` 已接收首片）
2. 发送方外观变化，新 STATE 到达
3. 接收端新请求 `req_B` → `setPendingRequest` 覆盖 pending，但不清除旧 assembly
4. `req_B` 首片到达 → `addRemoteChunk` 发现 assembly 仍属 `req_A` → 删除 assembly，抛 `remote-assembly-conflict`
5. `req_B` 首片丢失，发送方不会重发

**影响** 远端连续修改服装时，接收端可能长期看不到新版本。

**修复方向** `setPendingRequest` 在新请求与旧 pending（session/revision/hash 任一变）不一致时，显式清理旧 assembly：

```js
remoteStore.assemblies.delete(remotePeerKey(memberNumber));
```

### 4. CLEAR 后相同 hash 重新共享不触发新 REQUEST

**文件** `src/14-remote-controller.js:215`

**问题** STATE 处理条件只比较 `revision` 和 `hash`，不比较 `sharing` 状态转换。

**流程**

1. 接收端已有 snapshot
2. 发送端 CLEAR → 接收端清除 snapshot，peer.sharing = false
3. 发送端重新开启共享，外观未变 → 同一 revision + 同一 hash
4. `!previous || result.isNewSession || previous.revision !== envelope.r || previous.hash !== envelope.h` → false
5. `maybeRequestRemoteSnapshot` 不会调用
6. active snapshot 和 pending 都不存在

**影响** 用户切换共享开关后可能永远无法恢复远端显示，除非外观变化或重新入房。

**修复方向** 增加共享状态转换判断：

```js
previous.sharing !== envelope.sharing
```

特别是 `previous.sharing === false && envelope.sharing === true` 时强制发起 REQUEST。

### 5. 远端 revision 变化的 5 秒限流阻塞新快照

**文件** `src/14-remote-controller.js:154-165`

**流程**

1. 请求旧版本 A，pending 为 A，`requestTimes` 被设为 now
2. 5 秒内远端发布 B，STATE(B) 到达
3. pending.session/revision/hash 与 B 不匹配 → 不提前返回
4. `requestTimes` 仍在 5 秒窗口 → 新请求 B 被限流拒绝
5. 旧请求 A 的 timeout 只重试 A
6. B 没有恢复路径

**影响** 远端快速连续修改服装时，接收端可能卡在旧请求上。

**修复方向** 当 pending 与最新 peer 状态不一致时：

1. 清除旧 pending 和 assembly
2. 跳过 5 秒限流，立即发送新请求
3. 更新 `requestTimes`

## P2 数据一致性与安全性

### 6. 本地衣柜读取缺少 JSON.parse 前字节预算检查

**文件** `src/03-storage.js:12-31`

**问题**

- `MAX_WARDROBE_BYTES = 262144` 只在写入时检查
- 读取时没有检查原始 JSON 长度、LZ 解压后长度
- 构造一个 300KB 的 `json:` 数据：`status: ok`

**影响** 损坏或超大本地存储绕过预算，后续冲突比较或持久化可能抛出未捕获异常，初始化进入重试循环。

**修复方向**

在 `unpackWardrobeDetailed` 中 `JSON.parse` 之前：

```js
if (utf8Bytes(json) > MAX_WARDROBE_BYTES)
  return { status: "corrupt", error: "wardrobe-byte-budget" };
```

同时为 LZString 解压结果设置硬上限。

### 7. Visual Asset Proxy 保留了活动语义字段

**文件** `src/06-adapters.js:54-74`

**问题** `createVisualAssetProxy` 做 `...asset` 浅拷贝后，只清除了 `Archetype`、`AssetArchetype`、`Extended` 和三个 DynamicDraw 字段。以下字段仍然从源 Asset 保留：

- `FixedPosition`
- `SetPose`
- `OverrideHeight`
- `HeightModifier`
- `Hide` / `Block` / `Effect`

BC 上游 `CommonDrawComputeDrawingCoordinates` 明确使用 `asset.FixedPosition` 计算绘制坐标。

**影响** 所谓"静态图片投影"仍受源素材固定位置和身高语义影响，代理的行为与诊断结果不一致。

**修复方向**

方案 A：`analyzeSourceAsset` 返回 `compatibility=unsupported`（含 `formal-appearance-semantics` 或 `requiresFormalItem`）时，跳过该 material 的 synthetic 构建。
方案 B：在代理中把完整的活动语义字段置空：

```js
FixedPosition: undefined,
SetPose: undefined,
OverrideHeight: undefined,
HeightModifier: undefined,
Hide: [],
Block: [],
Effect: [],
```

### 8. 编辑器保存失败没有回滚内存衣柜

**文件** `src/10-editor.js:582-598`

**问题**

```js
wardrobe.schemes[existingIndex] = entry;
wardrobe.equippedIds.push(entry.id);
persistWardrobe();  // 这里可能抛异常
```

`persistWardrobe` 可能因预算超限（`scheme-byte-budget` / `wardrobe-byte-budget`）或 normalize 异常抛出。没有事务回滚：

- 内存已修改但存储未写
- 用户看得到已保存但刷新消失

`importWardrobe`（`15-bootstrap.js:89-93`）已有回滚模式，但保存路径没有复用。

**修复方向**

```js
const previousWardrobe = cloneJSON(wardrobe);
const previousEditingId = editingId;
try {
  persistWardrobe();
} catch (error) {
  wardrobe = previousWardrobe;
  editingId = previousEditingId;
  toast("保存失败: " + error.message, "error");
  return;
}
```

### 10. 用户脚本元数据与运行时版本不一致

**文件** `src/00-userscript-header.js:4` / `src/01-runtime.js:2`

| 位置 | 当前值 |
|------|--------|
| @version | `1.0.0` |
| VERSION | `"1.8.1"` |
| @downloadURL | `@main/...` |
| @updateURL | `@main/...` |

**问题**

- Tampermonkey 无法通过 @version 判断更新
- @downloadURL/@updateURL 指向 old main 分支，与当前 `single-layer-transform-rebuild` 不一致
- Loader（`dist/CustomOutfitEditorEchoMirror.loader.user.js`）指向 `layer-transform`，核心脚本指向 `main`，入口不统一

**修复方向**

同步为：

```js
// @version      1.8.1
// @downloadURL  https://cdn.jsdelivr.net/gh/stareyeXuanyeLin/BC-COE@{branch}/dist/CustomOutfitEditorEchoMirror.user.js
// @updateURL    https://cdn.jsdelivr.net/gh/stareyeXuanyeLin/BC-COE@{branch}/dist/CustomOutfitEditorEchoMirror.user.js
```

其中 `{branch}` 按当前实际发布分支填写。

### 13. `addAssetLayers` 颜色 fallback 中间值

**文件** `src/10-editor.js:539`

```js
colors: Array.isArray(sourceColor) ? sourceColor : asset.DefaultColor?.map(() => sourceColor),
```

当 `asset.DefaultColor` 为 `undefined` 时，`?.map()` 返回 `undefined`。建议：

```js
colors: Array.isArray(sourceColor) ? sourceColor : (asset.DefaultColor?.map(() => sourceColor) ?? []),
```

`ensureMaterialColors` 会后续补齐，但中间值不应是 `undefined`。
